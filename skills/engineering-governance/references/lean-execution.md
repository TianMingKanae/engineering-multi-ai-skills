# Lean execution with scoped independent review

One authorized task has one accountable implementer and one current thread. The implementer completes diagnosis, assigned fixes, host preparation and evidence delivery without administrative acknowledgment between ordinary steps. Adopt this profile explicitly in the target project; it does not override host instructions or grant every role unrestricted write access.

| Change | Next action | Review scope |
|---|---|---|
| Path, encoding, launcher, copy or log repair with unchanged semantics | Smallest assigned fix, preserve error, rerun affected check in a fresh root | Operational delta; no automatic new hypothesis gate |
| Missing free dependency in a task-local environment | Install only within existing authorization; record resolved version/import and recheck | Assess dependency semantics; an import success alone is insufficient |
| Changed criterion, input population, workload, precision, comparison or budget | Prospective amendment before new data/work | Independent review of changed contract and affected evidence |
| Accepted source/results unchanged | Reuse accepted hashes and disclose what was not rechecked | Do not reopen an entire audit for an unrelated helper |
| Real unresolved scope/resource/access choice | Prepare concrete options/evidence for H; continue independent authorized work | Human decision at the actual boundary |

## Delta review packet

Name the base accepted packet/hash, exact changed files and revision, affected invariants, failure/retry evidence and costs, tests/recomputation, unchanged accepted evidence, remaining unchecked conditions and proposed next action. Review the changed surface plus its dependencies. If the delta changes a foundational assumption, expand review appropriately; delta review is not permission to skip needed independent checking.

Use one concise operational receipt. Do not create duplicate prose/JSON summaries, new threads or approval cycles merely to acknowledge a repair. Use detailed rationale where a decision needs it. A path fix can change function resolution; pool/dependency changes can alter numerical behavior. Classify by observed invariants, not by the file's name. Preserve failed outcomes and budget debits after successful repairs.

## Flexible roles without self-certification

Roles describe responsibilities, not mandatory processes. C and V may share one independent review session if it authors independent checks and did not implement the result. This does not establish blindness if the session already saw solver code or the headline answer. Keep a separate minimal packet/session whenever blind verification is required. Likewise a research role may collect sources and tools without gaining production-code authority.

A standby identity is not a second active role. For provider or host replacement: record an ownership epoch, old provider stop evidence, in-flight job inventory and preserved immutable roots; transfer state, activate one effective successor, require actual task/receipt evidence, and retire obsolete routes. Do not terminate the old role's valid long-running jobs merely to move the conversation. Role merging never silently renames thread owners: migrate open assignments explicitly and stop retired watchers. Use [ROLES.md](../../../templates/project/context/ROLES.md).

| Concern | Before | Adopted lean profile |
|---|---|---|
| Administrative deadlock | Every repair waits for another coordinator acknowledgment | Assigned implementer continues within scope; genuine decisions reach H |
| Review/token overhead | Re-review all code and evidence after every receipt | One affected delta packet at the applicable milestone |
| Ambiguous readiness | Host inventory or stored test advertised as execution permission | Separate preparation, compatibility, release, execution and outcome evidence |
| Failure/cost erasure | Fresh root or provider appears to reset attempts | Stable budget/task authority retains failures and pending reservations |
| Role duplication | Old and replacement watchers both act | Stop/transfer/activate with one ownership epoch and task response |

These are mechanisms to evaluate, not measured speedups. Record completed work, gate latency, failure coverage and model cost under matched workloads before claiming savings. See [execution integrity](../../execution-integrity/SKILL.md) and [operational health](operational-health.md).
